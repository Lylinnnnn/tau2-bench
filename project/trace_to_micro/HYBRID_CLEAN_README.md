# Hybrid Clean Context Pipeline

This document describes the `hybrid_clean` context condition used by the
training-free same-state probe. It replaces neither the original trajectory nor
the earlier LLM-only compact conditions. Keeping all conditions makes it
possible to measure whether improvements come from the hybrid construction
rather than from changing the source rollout.

## Objective

The pipeline tests whether an agent makes a cleaner local decision when a long
trajectory prefix is replaced with:

1. a deterministic ledger of facts that were visible to the agent;
2. a short LLM-generated semantic brief grounded in that ledger; and
3. a deterministic action contract that states who must act, which response
   mode is valid, which inputs are missing, and which identifiers are bound.

The builder never reads the logged target action, future messages, reward,
hidden task atoms, evaluation criteria, or reference actions. Those values
remain evaluation-only.

## Pipeline

```text
logged prefix
    |
    v
verified evidence extractor (code only)
    |
    v
source quality flags
    |
    v
Semantic Brief generator (LLM)
    |
    v
deterministic semantic gate
    |-- pass ------------------------------|
    |-- semantic failure -> retry <= 2 ----|
    |-- still invalid -> rule fallback ----|
                                            v
                              Action Contract compiler
                                            |
                                            v
                              fresh agent model window
                                            |
                                            v
                              same-state one-step replay
```

An initial generation may be followed by at most two retries. Therefore one
snapshot makes at most three Semantic Brief calls. Tool ownership, identifier
binding, missing arguments, and terminal lifecycle are repaired by code and do
not consume an LLM retry.

## 1. Verified evidence

`build_verified_context` reads only messages that were valid in the agent's
history. User simulator tool calls and their raw tool responses are excluded.
It creates:

- `recent_dialogue`: bounded recent assistant/user text with evidence IDs;
- `tool_events`: assistant calls, ownership, executor validity, result status,
  and results capped at 1,200 serialized characters per event;
- `entities`: customer, line, bill, plan, device, and phone identifiers with
  their evidence source;
- `tool_ownership`: exact assistant and user tool registries;
- `terminal_state`: completed transfer and user-reported resolution;
- `interaction_phase`: identity collection, troubleshooting, error recovery,
  reported resolution, or completed transfer;
- `quality_flags`: currently includes a high-precision user-role-inversion
  signal.

Database replay remains the factual execution backend. The clean prompt does
not receive the full hidden database. Entity/state values are included only
when they appeared in an agent-visible user statement, assistant call, or
assistant tool response.

Entity extraction runs on the full parsed tool result before the model-facing
result is capped. Thus a long customer or bill response cannot inflate the
Semantic Brief prompt, while deterministic identifier binding still sees every
observed ID.

## 2. Semantic Brief

The context-builder LLM receives the verified evidence, not the full policy,
full tool schemas, or unbounded transcript. It returns:

```json
{
  "user_goal": "Restore mobile data while travelling.",
  "active_issue": "Airplane Mode is still enabled.",
  "situation_summary": "Account roaming is enabled but the device is offline.",
  "proposed_subgoal": "Help the user disable Airplane Mode.",
  "proposed_action": {
    "name": "toggle_airplane_mode",
    "executor": "user"
  },
  "success_evidence": "The user confirms Airplane Mode is disabled.",
  "evidence_ids": ["msg_23", "tool_8_0"]
}
```

The LLM may organize and summarize evidence. It may not invent identifiers,
tools, evidence IDs, or new facts. Tool arguments are never generated by this
stage.

## 3. Semantic validation and retry

The code gate currently checks:

- exact JSON shape and field types;
- evidence IDs exist;
- identifiers mentioned in the brief exist in the entity ledger;
- a proposed action exists in either tool registry;
- null action and `none` executor agree;
- a completed transfer is not proposed again;
- a user-reported resolution is not treated as an unresolved direct action;
- an invalid-executor tool failure is not proposed again;
- the success condition names observable evidence.

Validation emits structured error codes such as:

```json
{
  "code": "SUBGOAL_ALREADY_COMPLETED",
  "field": "proposed_subgoal",
  "message": "Transfer already succeeded; only confirm it to the user"
}
```

On retry, only affected fields are requested. For example, an invalid
`proposed_action` also regenerates its coupled subgoal, success evidence, and
evidence references. Valid unrelated fields are preserved. Two failed retries
produce a conservative rule fallback and `training_eligible=false`.

The following are code repairs, not retry reasons:

- mapping a user tool to `next_executor=user`;
- changing the response mode to `instruction`;
- binding an observed phone/customer/line/bill identifier;
- blocking a tool call until a required input is available;
- forcing transfer confirmation after transfer success.

## 4. Action Contract

The compiler converts the semantic proposal into a model-facing contract:

```json
{
  "next_executor": "user",
  "agent_response_mode": "instruction",
  "allowed_agent_tools": [],
  "required_inputs": [],
  "bound_arguments": {},
  "forbidden_actions": ["toggle_airplane_mode"],
  "completion_condition": "The user confirms Airplane Mode is disabled.",
  "repairs": []
}
```

Important cases:

- A missing phone number changes `get_customer_by_phone` into
  `request_information`; it never guesses a value.
- A user-owned device operation becomes an instruction, not an assistant tool
  call.
- A completed transfer allows no tools and requires confirmation text.
- A single grounded required identifier is bound by code. Ambiguous or missing
  identifiers become `required_inputs`.

## 5. Fresh-window inference

`hybrid_clean` sends a new stateless model request containing:

```text
System: the unchanged tau2 agent policy
User: verified context + Semantic Brief + Action Contract
Tools: the same full assistant tool list as the benchmark
```

The original prefix is not sent to the agent model. The environment is
independently reconstructed from the original prefix, so every paired variant
starts from the same factual pre-state.

`hybrid_clean_scoped_tools` is implemented as an optional ablation. It exposes
only tools allowed by the Action Contract. It is intentionally not enabled in
the default Qwen3-32B config, because tool scoping must be reported separately
from the context-only intervention.

### Real trajectory example: completed transfer

Simulation `ff61ec77-8182-4a88-8e71-73ce3094ff59` in the checked-in Qwen3-32B
Telecom results contains this late prefix:

```text
turn 63 user: persistent connection issue; requests escalation
turn 64 assistant: transfer_to_human_agents(...)
turn 65 tool: Transfer successful
turn 66 assistant target: transfer confirmation text
```

For the snapshot immediately before turn 66, the extractor sets
`terminal_state.transfer_completed=true`. Any Semantic Brief that proposes
another transfer fails with `SUBGOAL_ALREADY_COMPLETED`. The code-compiled
contract then has `agent_response_mode=text`, no allowed tools, and
`transfer_to_human_agents` in `forbidden_actions`. The fresh model window sees
that contract and the verified successful tool event, but never sees the logged
turn-66 target. This is the intended use of rules for hard lifecycle facts and
the LLM only for a readable local summary.

## 6. Training eligibility

The clean builder marks a context ineligible when:

- semantic generation falls back after two retries; or
- deterministic source checks flag suspected user-role inversion.

After the logged target is replayed, an evaluation-only source-action audit
also checks:

- the logged tool exists;
- the assistant is its valid executor; and
- the assistant tool execution succeeded.

The target audit is never included in model input. A row is training-eligible
only when both the context and source action pass. This prevents an exact
reproduction of a bad logged action from being treated as clean supervision.

## 7. Artifacts

For each split the pipeline writes:

```text
structured_contexts.jsonl  # earlier LLM-only conditions
hybrid_contexts.jsonl      # verified + semantic + contract contexts
paired_predictions.jsonl   # all paired variant outputs and audits
paired_probe_report.json
```

The report keeps every row in the primary benchmark-style metrics and also
provides `by_variant_training_eligible` as a source-quality-filtered diagnostic.
This avoids silently improving the headline result by dropping difficult or
invalid behavior-policy examples.

Each hybrid builder record includes:

- `attempt_count`;
- `retry_count` (never greater than 2);
- per-attempt token/timing metadata;
- structured validation errors;
- final status (`passed` or `rule_fallback`).

## 8. Running and resuming

From the repository root on the configured server:

```bash
project/trace_to_micro/scripts/run_qwen3_32b_model_preexperiment.sh
```

The Qwen3-32B config includes `hybrid_clean`. Existing `long_raw`,
`structured_state`, and `clean_subtask` rows are reused. The resumable probe
builds `hybrid_contexts.jsonl` and generates only missing `hybrid_clean` rows.
It also backfills source-action audit fields on legacy prediction rows from
deterministic replay; this does not make another agent-model call.
Trajectory generation and trajectory analysis are not repeated when their
artifacts are complete.

To run only the model probe and summary against an already complete source
result:

```bash
export PYTHONPATH="$PWD/project/trace_to_micro/src${PYTHONPATH:+:$PYTHONPATH}"
CONFIG=project/trace_to_micro/configs/qwen3_32b_thinking_model_preexperiment.toml

uv run --no-sync python -m trace_to_micro.cli paired-probe --config "$CONFIG"
uv run --no-sync python -m trace_to_micro.cli summarize-probe --config "$CONFIG"
```

## 9. Tests

```bash
uv run pytest -c project/trace_to_micro/pyproject.toml \
  project/trace_to_micro/tests
```

The regression tests cover completed-transfer handling, missing identifiers,
entity binding, user-tool executor correction, role-inversion flags, semantic
evidence validation, bounded two-retry behavior, fallback, and fresh-window
construction. Tests use fake generation functions and make no live model calls.
